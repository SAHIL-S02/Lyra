LYRA 2.0 — COMPLETE PROJECT SPECIFICATION / BUILD CONTEXT
===========================================================

PURPOSE
-------
Lyra 2.0 is a new-from-scratch personal AI voice assistant designed to be
LOCAL-FIRST, WEB-ASSISTED, TOOL-AWARE, VOICE-DRIVEN, and deployable on a
CPU-only final machine.

This document is intended to be supplied to an AI coding agent such as
Antigravity as the primary project context.

The user should experience only one assistant:
    LYRA

Internal models/providers are implementation details. Do not make Lyra's
identity depend on a particular AI provider.


1. LYRA 1.0 AND LYRA 2.0
========================

LYRA 1.0
--------
Lyra 1.0 is an already-working project and should be preserved as a stable
version. Its main architecture used Gemini Live, local wake-word detection,
voice input/output, persistent SQLite memory, tool calling, inactivity sleep,
and barge-in.

Lyra 1.0 should remain frozen while 2.0 is developed.

The stable release was tagged:
    v1.0.0

LYRA 2.0
--------
Lyra 2.0 is a NEW project built from scratch.

Do not simply modify Lyra 1.0 into 2.0.
Do not make Gemini Live the main brain.

The new primary architecture is:

    Wake Word
        ↓
    STT
        ↓
    AI Router
        ↓
    Local LLM by default
        ↓
    Web search when fresh/external information is needed
        ↓
    Tools when action/data access is required
        ↓
    TTS
        ↓
    Speaker


2. CORE PRODUCT GOAL
====================

NORMAL REQUESTS
---------------
Use the local LLM.

Example:
    User: "Explain recursion."
    Router: LOCAL
    LLM: Qwen3 1.7B
    TTS: speak answer

CURRENT / EXTERNAL INFORMATION
------------------------------
Use web search, then provide the retrieved information to the local LLM
for synthesis.

Example:
    User: "What is the latest Python release?"
    Router: WEB / HYBRID
    Search: obtain current information
    Local LLM: synthesize answer
    TTS: speak answer

TOOL REQUEST
------------
Use the appropriate tool.

Example:
    User: "What time is it?"
    Router: TOOL
    Tool: get_current_time

The user should not have to know whether the answer came from a local model,
web retrieval, or a tool.

FINAL DEPLOYMENT MACHINE

Design for:

The actual AMD CPU should be benchmarked before finalizing model/STT/TTS
settings. A dual-core CPU may become the latency bottleneck even though 16 GB
RAM is sufficient for a small model.

6. ROUTING MODES
================

The router should support these modes:

    LOCAL
    WEB
    TOOL
    HYBRID

LOCAL
-----
Use for normal timeless requests that are suitable for the local model.

Examples:
- explanations
- writing
- brainstorming
- simple coding help
- normal conversation
- basic reasoning

WEB
---
Use when information must be current or externally verified.

Examples:
- latest news
- today's events
- current weather
- current prices
- latest software versions
- recent releases
- current company/technology information
- user explicitly says search/look up/check online

TOOL
----
Use for deterministic actions/data retrieval through an application tool.

Examples:
- time/date
- system information
- memory actions
- Spotify commands
- smart-home commands
- application control

HYBRID
------
Use when web/tool output must be passed into the local LLM to produce the
final natural-language answer.


7. ROUTER DESIGN PRINCIPLES
===========================

Do NOT trust a small local LLM's self-reported confidence as the sole signal
for whether it knows something.

The router should use explicit deterministic signals plus model/task logic.

Current-information triggers can include:
- latest
- today
- current
- recent
- live
- this week
- this month
- current version
- current price
- weather
- news
- score
- release
- recent update

Explicit search triggers can include:
- search the web
- search online
- look up
- find online
- check the internet
- search for

The router should eventually consider:
1. Does this require current information?
2. Does this require an external tool?
3. Does this use private/local information?
4. Does this require complex reasoning?
5. Is internet available?
6. Is low latency important?
7. Is the request suitable for the local model?

If internet is unavailable, normal LOCAL requests must continue to work.

If a request requires current information and web access fails, Lyra must NOT
fabricate the current answer.


8. WEB SEARCH
=============

Web search should be provider-independent.

Desired flow:

    User request
        ↓
    Search provider
        ↓
    Relevant retrieved information
        ↓
    Local Qwen3
        ↓
    Final answer

Do not permanently hard-code one search provider into the entire Lyra
architecture.

Potential providers can be swapped later.

The web layer should return structured results such as:
- title
- URL/source
- snippet/content
- publication date when available
- source metadata when available

Do not over-search ordinary questions.

10. WAKE WORD
=============

Wake word:
    "Hey Lyra"

A custom Hey Lyra model has already been trained for Lyra 1.0.
Reusable assets include:
- hey_lyra.onnx
- hey_lyra.tflite

The wake-word system was based on openWakeWord.

A previous training run produced approximately:
- accuracy: 0.8625
- recall: 0.7324
- false positives/hour: 8.67

Do not retrain unnecessarily.
Reuse the trained Hey Lyra model where practical.

Wake word MUST be local and work while the internet is unavailable.


11. STT
=======

Technology:
    faster-whisper

Previously tested:
- faster-whisper large-v3-turbo style setup
- CUDA on RTX 4050
- float16
- CTranslate2 CUDA device detected

DEVELOPMENT:
    use GPU acceleration where appropriate

FINAL CPU MACHINE:
    use CPU-compatible inference
    prefer int8 for resource efficiency

The final AMD dual-core machine may need a smaller STT model than the
large development model. Benchmark accuracy vs latency before finalizing.

STT must be provider-independent inside Lyra. The rest of the system should
not depend on faster-whisper-specific classes.


12. TTS
=======

TTS must be local.

Previously tested:
    Kokoro TTS

Potential CPU-friendly alternative:
    Piper or another lightweight local TTS

Do not make cloud TTS mandatory.

The TTS layer should support:
- low latency
- local inference
- interruption/stop
- configurable voice/provider


13. BARGE-IN
===========

Desired behavior:

    Lyra is speaking
        ↓
    User starts speaking
        ↓
    Stop/discard current playback immediately
        ↓
    Listen/process the new request

The playback system should support:
- queued audio
- immediate clear/discard
- low-latency interruption

A response that has been interrupted must not continue playing afterward.


14. AUTO-SLEEP
==============

Lyra should sleep after configurable inactivity.

Existing tested value:
    30 seconds

Desired flow:

    Active conversation
        ↓
    No user speech for timeout
        ↓
    End active processing/session if needed
        ↓
    Sleeping
        ↓
    Local wake-word listener remains active

When sleeping, avoid unnecessary cloud/network activity.


15. STATE MACHINE
=================

Use explicit states.

Suggested states:

    SLEEPING
    WAKE_DETECTED
    LISTENING
    PROCESSING
    SPEAKING
    IDLE
    ERROR

Suggested flow:

    SLEEPING
       ↓
    WAKE_DETECTED
       ↓
    LISTENING
       ↓
    PROCESSING
       ↓
    SPEAKING
       ↓
    IDLE
       ↓
    SLEEPING

Errors should recover safely rather than killing the whole assistant.


16. MEMORY
==========

Lyra requires persistent long-term memory.

Memory is separate from model weights.

Recommended storage:
    SQLite

Previously established fields:
- id
- key
- value
- category
- retention
- source
- created_at
- updated_at
- last_accessed_at

Categories:
- fact
- preference
- event
- profile
- other

Retention:
- permanent
- episodic

Important behavior:
Do NOT save every casual sentence.

Explicit memory requests should create/update memory.

Examples:

    "Remember that my favorite language is Java."
        -> remember_memory

    "What is my favorite language?"
        -> search_memory

    "Change my favorite language to Python."
        -> find existing key
        -> update_memory

    "Forget my favorite language."
        -> forget_memory

Memory remains an external editable database property, not fine-tuning.


17. MEMORY KEY NORMALIZATION
============================

Canonical keys are important.

Example aliases that must not create separate memories:

    creator_name
    creator_full_name
    my_creator
    assistant_creator
    lyra_creator

Canonical key:
    creator

Similarly:

    version
    lyra_version

should resolve to:
    system_version

When changing an existing memory:
1. search for the existing record when required
2. use its exact key/category
3. update the existing memory
4. do not invent a duplicate alias


18. TOOL SYSTEM
===============

Use a centralized Tool Registry and Tool Executor.

Architecture:

    Tool Definition
        ↓
    Tool Registry
        ↓
    Tool Executor
        ↓
    Actual Tool
        ↓
    Structured Result

ToolDefinition should contain:
- name
- description
- handler
- parameters/schema
- requires_confirmation

Registry responsibilities:
- register tools
- reject duplicate names
- list tools
- retrieve a specific tool
- provide model-facing declarations/schema

Executor responsibilities:
- confirm that tool exists
- execute sync and async handlers
- catch failures
- return structured results
- enforce confirmation requirement

Example success result:

    {
        "success": True,
        "tool": "get_current_time",
        "result": {...}
    }

Example failure:

    {
        "success": False,
        "tool": "unknown_tool",
        "error": "Unknown tool: unknown_tool"
    }

20. TOOL SECURITY
=================

NEVER provide unrestricted shell execution to the LLM.

Do not implement:
    execute_shell_command(user_input)

All actions must go through explicit, validated tools.

Suggested permission levels:

SAFE:
- current time/date
- system status
- non-sensitive information

CONFIRMATION:
- open an application
- send a message
- change media state
- non-destructive external actions

SENSITIVE:
- delete files
- shutdown/restart
- locks
- financial actions
- account operations
- irreversible changes

Sensitive actions should require explicit confirmation and eventually
authentication.

Potential providers:
- Ollama local
- Gemini (optional)

- future local runtimes

The core should not know which provider is active.

25. LOCAL PROVIDER
==================

Local provider implementation:
    Ollama

Default configuration:

    OLLAMA_HOST=http://localhost:11434
    OLLAMA_MODEL=qwen3:1.7b

Provider requirements:
- health check server
- verify model installed
- send chat request
- handle timeout
- handle connection errors
- return clean text

- expose model/provider status

Use an abstraction so Ollama can later be replaced without changing the
router or voice controller.

34. CLOUD PROVIDERS
===================

Gemini Live was the main provider in Lyra 1.0.

For 2.0, Gemini is OPTIONAL.

Reasons for making it optional:
- API quota/rate limits
- provider independence
- local-first goal
- final CPU-only deployment
- offline operation

Potential future cloud role:
- complex reasoning
- optional voice mode
- fallback
- special tasks
- model comparison/evaluation

But Lyra 2.0 basic functionality MUST NOT depend on Gemini.

36. ERROR RECOVERY
==================

Ollama unavailable:
    report local provider unavailable
    optionally use an explicitly configured fallback
    keep wake-word system alive if possible

STT failure:
    return safely to listening/wake state

TTS failure:
    log and recover

Web failure:
    return structured failure
    do not hallucinate current information

Tool failure:
    return structured failure to the LLM
    allow natural user-facing explanation

Unexpected errors:
    log
    recover/reinitialize affected subsystem when possible
    keep main assistant alive

40. ANTIGRAVITY BUILD RULES
===========================

Use these rules when an AI coding agent builds Lyra 2.0:

1. Lyra 2.0 is a fresh project.
2. Keep Lyra 1.0 untouched.
3. Build incrementally.
4. Test each subsystem independently.
5. Never rewrite the whole project unnecessarily.
6. Preserve already-tested assets where appropriate.
7. Keep provider implementations behind an abstraction.
8. Keep tool implementations behind the registry/executor.
9. Never expose arbitrary shell execution.
10. Keep secrets outside Git.
11. Prefer local inference.
12. Use web only when needed.
13. Web search is retrieval, not a second brain.
14. Pass web results to the local model for synthesis.
15. Make state transitions explicit.
16. Support barge-in and cancellation.
17. Support inactivity sleep.
18. Design for CPU-only final hardware.
19. Do not require NVIDIA/CUDA in the final deployment.
20. Make settings configurable.
21. Do not use Lyra 1.0's database directly.
22. Do not fabricate current information when web is unavailable.
23. Do not assume the local model can reliably judge its own knowledge.
24. Keep the assistant identity as Lyra independent of the backend model.
25. Create tests alongside features.
